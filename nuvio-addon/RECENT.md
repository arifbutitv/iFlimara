# المضاف حديثاً

الإصدار 1.10.0 يضيف فهرسًا مركزيًا يجمع قوائم الأفلام والمسلسلات والبرامج من آي فيلم والكوثر وShiaTube ويوتيوب وDailymotion. تُستبعد TV Live وجدول البث. يقع التصنيف بعد جدول البث، وتبقى القوائم السابقة بترتيبها النسبي.

## البروتوكول والتطبيق

| الحقل | القيمة |
| --- | --- |
| اسم التصنيف | المضاف حديثاً |
| معرّف التصنيف | `ifilmar-recent` |
| نوع التصنيف المختلط | `other` |
| الطلب الأول | `/catalog/other/ifilmar-recent.json` |
| البحث | `/catalog/other/ifilmar-recent/search=الكلمة.json`، مع ترميز الكلمة |
| الصفحة التالية | `/catalog/other/ifilmar-recent/skip=100&revision=1.json` |
| حجم الصفحة | 100 عنصر |

`other` هو نوع القائمة المختلطة فقط. كل عنصر يحمل نوعه الأصلي `movie` أو `series` ومعرّفه الأصلي. يفتح التطبيق `/meta/{item.type}/{item.id}.json`، ويطلب `/stream/movie/{item.id}.json` للفيلم. للمسلسل أو البرنامج يختار المستخدم حلقة من `meta.videos` ثم يطلب `/stream/series/{video.id}.json`. ترتبط هذه المسارات بالمزوّدين الحاليين كما في القوائم الأصلية.

على تطبيق iFilm عرض التصنيف الوارد في manifest وإرسال `skip` و`search` إلى الخادم، واستعمال `item.type` عند فتح التفاصيل. يحفظ التطبيق `recentRevision` من الصفحة الأولى ويرسله مع الصفحات التالية لضمان عدم تكرار العناصر أو فقدها أثناء وصول تحديث. يُصفّر `skip` ونسخة التصفح عند تغيير البحث أو تحديث القائمة. يُستبدل الرصد المحلي ودمج القوائم وترتيبها بهذه الاستجابة المركزية. يحتاج العميل الذي يدعم أنواعًا ثابتة إلى إضافة دعم عرض قائمة `other` مختلطة.

يحتفظ السجل بآخر 12 ترتيبًا منشورًا. إذا انقضت النسخة المطلوبة يعيد الخادم HTTP 409 مع `RECENT_REVISION_EXPIRED`، ويبدأ التطبيق التصفح من `skip=0`. ترتيب الأسماء المستخدمة في البحث محفوظ مع نسخة التصفح حتى عند تصحيح عنوان أثناء التصفح. يُظهر العميل الذي يرسل `skip` فقط أحدث ترتيب متاح، لذلك يلزم إرسال `revision` لضمان ثبات الصفحات عبر التحديثات.

مثال توضيحي لعنصرين من الدفعة التأسيسية

```json
{
  "metas": [
    {
      "id": "ifilmar:movie:74595",
      "type": "movie",
      "name": "المعطر (2022)",
      "firstSeenAt": "2026-11-27T04:15:51.592Z",
      "addedAt": null,
      "addedAtSource": "unknown"
    },
    {
      "id": "ifilmar-program:41726",
      "type": "series",
      "name": "فيلم سيناريو",
      "firstSeenAt": "2026-11-27T04:15:51.592Z",
      "addedAt": null,
      "addedAtSource": "unknown"
    }
  ],
  "recentRevision": 1,
  "recentUpdatedAt": "2026-11-27T04:15:51.592Z",
  "cacheMaxAge": 60
}
```

حقول الصور والوصف الأصلية تُعاد أيضًا عند توفرها. في المثال يفتح الفيلم عبر `/meta/movie/ifilmar:movie:74595.json`، والبرنامج عبر `/meta/series/ifilmar-program:41726.json`. معرّف حلقة البرنامج يُؤخذ من التفاصيل وليس من معرّف القائمة الموحدة.

## الرصد والهوية والتوقيت

تُطابق عناصر آي فيلم والكوثر بمعرّفها الرقمي الأصلي، بما في ذلك ظهور المعرّف نفسه في أكثر من قائمة. قوائم يوتيوب وDailymotion تستخدم معرّف قائمة التشغيل. أفلام ShiaTube تستخدم معرّف الفيديو، ومسلسلاته تستخدم معرّفات حلقاتها الأصلية كأسماء بديلة لهوية العمل، حتى لا يغير تصحيح اسم المجموعة وقت اكتشافها. تشابه الأسماء بين أعمال أو مصادر مختلفة لا يكفي للدمج. يبقى مسار التفاصيل الأصلي للممثل الأول للعمل، مع تحديث بيانات ذلك المزوّد عند رصده مجددًا.

التاريخ الموثوق المتاح حاليًا هو `created_time` لقائمة Dailymotion، ويعبّر عن إنشاء قائمة التشغيل. تُضاف محولات موثوقة لبقية المصادر فقط عند وجود حقل صريح صالح لهذا الغرض. لا تُستخدم سنة الإنتاج، أو `releaseInfo`، أو تاريخ إصدار العمل، أو تاريخ أحدث حلقة لترتيب العمل كله.

يُسجّل `firstSeenAt` مرة واحدة بتوقيت UTC. في التهيئة الأولى يحتفظ العمل بهذا الوقت بوصفه وقت اكتشاف الفهرس، وتبقى `addedAt` بقيمة `null` و`addedAtSource` بقيمة `unknown` إذا غاب تاريخ المصدر. تُعرض هذه الأعمال بعد الأعمال ذات تاريخ الإضافة المعروف. إذا وفر المصدر تاريخًا حقيقيًا يُستخدم مع `addedAtSource=source`. بعد اكتمال تأسيس المصدر، يحمل العمل الجديد في صفحة رأس القائمة `addedAt=firstSeenAt` و`addedAtSource=firstSeen` عند غياب تاريخ المصدر.

تحديث الاسم أو البوستر، أو إضافة حلقة إلى مسلسل موجود، أو إعادة جلب البيانات يحافظ على `firstSeenAt`. تسجّل الميزة الأعمال والقوائم الجديدة، وتبقى الحلقات ضمن تفاصيل عملها. يُحسم تساوي التواريخ بمفتاح الهوية الأصلي الثابت.

لكل مصدر مؤشر تأسيس مستقل وموضع لاستكمال الصفحات. يُفحص رأس القائمة كل دورة، وتُستكمل الصفحات القديمة تدريجيًا. المحتوى المكتشف أثناء التأسيس أو في صفحات الاستكمال يُعامل كقديم مجهول التاريخ عند غياب تاريخ موثوق، حتى لو اكتُشف بعد تشغيل الميزة. هذا اختيار محافظ لتجنب تقديم الأرشيف باعتباره جديدًا. فشل صفحة يلغي تطبيق تحديث مصدرها كله ويحافظ على بياناته ومؤشره السابقين. لا تحذف الميزة العمل لمجرد غيابه عن استجابة لاحقة.

## التخزين الدائم والتشغيل

السجل المرجعي هو `recent.json` في الفرع المستقل `content-index` داخل مستودع GitHub العام الحالي. تُحفظ فيه سجلات الهوية و`firstSeenAt` وحالة تأسيس كل مصدر وترتيبات التصفح. حفظه في Git يبقيه عبر إعادة تشغيل Render وإعادة نشر الخدمة. ملفات checkout وملفات القفل أدوات عمل للمهمة، وملف الفرع المنشور هو النسخة الدائمة المعتمدة. تحديث هذا الفرع لا يعيد بناء الخدمة المرتبطة بفرع `main`.

تعمل مهمة `Update central recent catalog` في `.github/workflows/recent.yml` عند الدقيقتين 17 و47 من كل ساعة UTC، مستقلة عن فتح التطبيقات أو نشاط Render. يحتاج المستودع إلى تفعيل GitHub Actions والسماح للمهمة بكتابة محتويات فرع `content-index`. تستخدم المهمة رمز GitHub المؤقت الممنوح لها، دون وضع رمز في كود الإضافة أو إعدادات التطبيق. يحتاج الإنشاء الأول إلى وجود الفرع وملف حالة صالح، ويُجهزان مع هذا الإصدار.

تمنع مجموعة concurrency تداخل مهام النشر. يُستخدم قفل حصري للملف عند تشغيل العامل محليًا، ثم كتابة ملف جديد وإعادة تسميته ذرّيًا. يرفض Git الدفع المتعارض بدل استبدال نسخة أحدث بالقوة. فشل أحد المصادر يُحفظ في حالة المصدر مع بقاء محتواه، وتستمر المصادر الأخرى.

كل دورة افتراضية تعالج ثلاثة صفحات كحد أقصى لكل مصدر، مع مصدرين متوازيين. مزودا آي فيلم والكوثر الحاليان قد يجلبان صفحات داخلية أثناء بناء صفحة الكتالوج، ويستفيدان من كاشهما. تتجدد هذه الكاشات داخل عملية عامل جديدة كل دورة. ShiaTube يُرصد من أحدث فهرس منشور في `main`، ويستمر وصول محتواه الأصلي وفق مُحدّثه المحلي الحالي. تكرار رصد الفهرس كل 30 دقيقة لا يسرّع نشر ذلك المصدر من جهاز المالك.

تقرأ خدمة الإضافة ملف الفرع فقط عند البدء، ثم تتحقق منه كل دقيقة وهي عاملة باستخدام ETag. طلبات التصنيف تستخدم الفهرس في الذاكرة ولا تجلب المصادر. الذاكرة كاش لنسخة دائمة منشورة، وتُستعاد البيانات من الفرع بعد إعادة التشغيل. إذا فشل تحميل نسخة جديدة تبقى آخر نسخة سليمة. عند أول تشغيل دون فهرس متاح يعيد التصنيف HTTP 503 حتى ينجح التحميل، وتبقى الخدمة قادرة على تقديم القوائم الأخرى.

متغير `RECENT_INDEX_URL` اختياري لتغيير رابط القراءة عند نقل المستودع، وقيمته الافتراضية

```text
https://raw.githubusercontent.com/arifbutitv/iFlimara/content-index/recent.json
```

للتشغيل المحلي للعامل اضبط `RECENT_INDEX_FILE` على مسار مطلق لملف السجل في checkout لفرع الحالة، ثم شغّل `node scripts/update-recent.js`. يمكن تغيير عدد صفحات الدورة عبر `RECENT_PAGE_BUDGET` بين 1 و100. يرفض العامل غياب الملف بدل إعادة ضبط أول ظهور. يحتاج إنشاء سجل أول جديد إلى `RECENT_BOOTSTRAP=1`، ويُستخدم ذلك مرة واحدة فقط عند غياب سجل سابق. لا تنشئ سجلًا فارغًا فوق سجل قائم، لأن ذلك يفقد أوقات أول ظهور. قفل محلي متبقٍ بعد انهيار عملية يحتاج التحقق من انتهاء تلك العملية قبل إزالته.

جدولة GitHub Actions بفاصل 30 دقيقة هي جدولة بأفضل جهد، وقد تتأخر أو تُسقط بعض التشغيلات أثناء ضغط المنصة. كما قد تُعطّل الجدولة في مستودع عام بعد فترة الخمول التي توضحها GitHub. إذا كان المطلوب موعدًا مضمونًا كل 30 دقيقة فيجب تشغيل العامل نفسه بمجدول خارجي دائم، مع الإبقاء على فرع الحالة ومصدر واحد للكتابة. خطة Render المجانية وحدها تتوقف عند الخمول ولا توفر هذا الضمان.

يلزم نشر الإصدار 1.10.0 في Render مرة واحدة ثم تحديث تعريف الإضافة في العميل. لا يلزم نشر الخدمة لكل تحديث فهرس.
